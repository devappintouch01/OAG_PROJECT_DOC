# คำขอโอนเงินกลับ → ให้หน้าโอนเงินกลับดึงไปทำต่อ (2026-10-14)

## Requirement
หน้าใหม่สำหรับส่งเรื่องว่า "เลขที่โอนจัดสรร (ROUNDNO) นี้มีรายการที่โอนกลับได้แล้ว"
เก็บข้อมูลเหมือนหน้า `BudgetTransferDetail` ทั้งหมด **ยกเว้นบัญชีผู้รับโอน**
บันทึกและส่งเรื่องแล้ว หน้าโอนเงินกลับมีกล่องรายการรอดำเนินการ เลือกแล้วระบบเติมรายการให้ ไม่ต้องค้นหาและเลือกเอง

## ข้อตกลงกับผู้ใช้
| # | เรื่อง | ข้อสรุป |
|---|---|---|
| 1 | "เลขที่โอน" | ROUNDNO ของใบโอนจัดสรร |
| 2 | Role | ยังไม่ใช้ แต่ต้องมีจุดให้ใส่เงื่อนไขในอนาคต |
| 3 | การแจ้งเตือน | กล่องบนหน้าโอนเงินกลับ ส่วนกระดิ่ง header แยกเป็นงานต่างหาก (ระบบเดิมใช้ไม่ได้จริง: SYSTEMNOTIFICATION ว่าง และไม่มี API) |
| 4 | การดึง | ดึงบางส่วนได้ และรวมหลายคำขอเป็นใบเดียวได้ |
| 5 | อนุมัติ | ตอนนี้ส่งแล้วไปรอเลย แต่ต้องรองรับขั้นอนุมัติในอนาคต |
| – | แก้ไขหลังดึง | หน้าโอนเงินกลับแก้ไขได้ตามปกติ |

## ข้อเท็จจริงที่ตรวจแล้ว (PREPROD / code)
- `SaveBudgetTransferDetailV2` ตัด `BUDGETRECEIVE` ทันทีตอนบันทึก จึงใช้ `BUDGETTRANSFER` เก็บคำขอไม่ได้
- แท็บ 3 อ่านจาก `V_BUDGETRECEIVEREFUND_COSTCENTER` ซึ่ง join จาก link `BUDGETRECEIVEREFUND` ที่มีหลังบันทึกเท่านั้น
- แถวที่เลือกมี key เป็น `V_BUDGETRECEIVESUMMARY_REFUND.ID` = `BUDGETRECEIVE.ID`
- `BUDGETALLOCATETRANSFER.ROUNDNO` ไม่ unique 100% (2,394 แถว / 2,391 ค่า มีซ้ำ 2 คู่ เป็นใบร่าง) จึงเก็บ ID คู่ไว้ด้วย
- dropdown ROUNDNO ที่มีอยู่: `MasterService.GetAllocateRoundNoWithFilter` (transferType '1' / '4')
- `MASTERSTATUS` ช่วง 70xxx ว่าง และไม่มีใน code
- Oracle 19c, NLS = TH8TISASCII / BYTE

## โครงสร้าง (ดู `01_create_tables.sql`)
- `OAGWBG_BUDGETTRANSFERREQUEST`: หัวคำขอ, สถานะ, คอลัมน์สำรองสำหรับอนุมัติ (`APPROVE*`) และ role (`TARGETROLEID`)
- `OAGWBG_BUDGETTRANSFERREQUESTITEM`: รายการ + **การผูกกับใบโอนกลับระดับรายการ** (`BUDGETTRANSFERID`, `PULLEDAMOUNT`)
- `OAGWBG_BUDGETTRANSFERREQUEST_COSTCENTER`: บัญชีผู้โอนต่อ (ศูนย์ต้นทุน, แผน, ประเภทรายจ่าย)

ไม่เพิ่มคอลัมน์ใน `OAGWBG_BUDGETTRANSFER` ฝั่งคำขอเป็นฝ่ายชี้ไปหาใบโอนกลับ จึง rollback ได้โดยไม่กระทบตารางเดิม

### สถานะ
```
ตอนนี้ : 70101 ร่าง → 70201 ส่งเรื่องแล้ว ──────────────────────→ 70601 ดำเนินการครบแล้ว
อนาคต  : 70101 ร่าง → 70301 รออนุมัติ → 70401 อนุมัติแล้ว ──→ 70601
ยกเลิก : 70501 (ได้เฉพาะเมื่อยังไม่มีรายการถูกดึง)
```
- สถานะที่ดึงได้ = `{70201, 70401}` รวมไว้ที่ค่าคงที่ตัวเดียว
- ตอนส่งเรื่องเลือก 70201 หรือ 70301 ตาม config `BudgetTransferRequest:RequireApproval` (ตอนนี้ = false)
- "ดึงบางส่วน" ไม่เก็บเป็นสถานะ แต่คำนวณจาก item (มีบางแถวที่ `BUDGETTRANSFERID` ไม่เป็น null)

### จุดเผื่อ role
คิวรีรายการรอดำเนินการผ่านเมธอดเดียว `ApplyRequestVisibility(query, user)` ตอนนี้คืน query เดิมไม่กรองอะไร
ในอนาคตใส่เงื่อนไข `TARGETROLEID` หรือหน่วยงานที่จุดนี้จุดเดียว

## Flow การดึงในหน้าโอนเงินกลับ
1. ใบใหม่ (หรือใบร่าง) จะแสดงกล่อง "คำขอรอดำเนินการ (n)" โดยเลือกได้หลายคำขอ หรือเลือกเป็นรายแถว
2. API `GetBudgetTransferRequestRows(itemIds)` คืนข้อมูลรูปแบบเดียวกับ `SearchBudgetTransferDetail`
   แต่กรองด้วย `BUDGETRECEIVEID` และ**คำนวณ FundsAvailable ใหม่ ณ วันที่ดึง**
   ต้องแยก logic คำนวณยอดออกจาก `SearchBudgetTransferDetail` เป็น helper ใช้ร่วมกัน
3. หน้าจอ render ลงแท็บ 1 และติ๊กแถวพร้อมยอดคำขอผ่าน `__selectionState` ที่มีอยู่แล้ว ทำให้แท็บ 2 ได้ข้อมูลอัตโนมัติ
   ส่วนหัวเติมจากคำขอแรก และ REFNO ("โอนจัดสรรรอบที่") = ROUNDNO ของคำขอ ถ้ามีหลายคำขอให้ต่อกันด้วย ", " (เพดาน 200 ตัวอักษร)
4. แต่ละแถวในแท็บ 2 ถือ `requestItemIds[]` ไว้ ถ้าคำขอต่างกันชี้ `BUDGETRECEIVEID` เดียวกัน ให้รวมยอดเป็นแถวเดียว
5. ผู้ใช้แก้ไขได้ตามปกติ
6. `SaveBudgetTransferDetailV2` รับ `requestItemIds` ต่อแถว แล้วทำใน transaction เดียวกัน:
   - ตรวจว่า item ยังไม่ถูกใบอื่นดึงไป (`BUDGETTRANSFERID IS NULL OR = ใบนี้`) ถ้าชนให้ rollback
   - set `BUDGETTRANSFERID`, `PULLEDAMOUNT`, `PULLBY`, `PULLON`
   - item ที่เคยผูกกับใบนี้แต่ไม่อยู่ใน payload แล้ว (ผู้ใช้ลบแถว) ให้คืนเป็น null เพื่อกลับไปรอดำเนินการ
   - copy บัญชีผู้โอนจาก `REQUEST_COSTCENTER` ลง `BUDGETRECEIVEREFUND_COSTCENTER` (`BANKACCOUNTID` = null)
     ทำเฉพาะ key ที่ยังไม่มีแถว ถ้าหลายคำขอให้บัญชีต่างกัน ใช้ของคำขอแรก แล้วผู้ใช้แก้เองในแท็บ 3
   - คำขอที่ item ถูกดึงครบทุกแถว ให้เปลี่ยนเป็น 70601 ถ้าถูกคืนแถว ให้ถอยกลับเป็น 70201/70401
7. หลังบันทึก แท็บ 3 มีบัญชีผู้โอนแล้ว ผู้ใช้เลือกบัญชีผู้รับโอนแล้วจองงบต่อตามเดิม

## ข้อสมมติ (ผู้ใช้รับทราบ 2026-10-14)
- ดึงบางส่วน**นับเป็นรายแถว** ถ้าผู้ใช้แก้ยอดน้อยกว่าที่ขอ แถวนั้นถือว่าดำเนินการแล้ว ส่วนต่างไม่กลับไปรอ
- ถ้าใบโอนกลับถูก**ยกเลิกการยืนยัน (80501)** ให้คืน item ของใบนั้นกลับไปรอดำเนินการ เพราะงบถูกคืนแล้ว
- เลขที่คำขอ: `RQ` + ปี 2 หลัก + running 4 หลัก ต่อปี (เช่น RQ690001)

## สิ่งที่ implement จริง (ต่างจากแผนด้านบน)
- **เลขที่คำขอ** ใช้ `OAGWBG_TRANSFER_RUNNING` key `ORG_TYPE = 'RQ'` (MERGE atomic แบบเดียวกับ ResolveRoundNoAsync)
  ตรวจแล้วทุกจุดที่ใช้ตารางนี้ key ด้วย (BUDGET_YEAR, ORG_TYPE) เสมอ ใบโอนใช้ ORG_TYPE เป็นตัวเลข จึงไม่ชน
- **การจับคู่ item กับใบโอนกลับ** ไม่ใช้ BUDGETRECEIVE.ID เพราะ
  (1) แถวที่เปิดจากใบเดิมใช้ ID ของ view link ไม่ใช่ BUDGETRECEIVE.ID
  (2) V2 เลือก giver เองตามยอดคงเหลือมากสุด อาจไม่ใช่แถวที่ผู้ขอเลือก
  → จับคู่ด้วย "บรรทัดงบ" (หน่วยเบิกจ่าย, ศูนย์ต้นทุน, ปี, หมวด, ผลผลิต, ใบเงินกัน) กับ link ของใบหลังบันทึก
  แถวปกติ (ไม่ใช่เงินกัน) จับคู่โดยไม่สนใบเงินกัน เพราะ V2 ไม่ได้กรองใบเงินกันให้แถวปกติ
  PULLEDAMOUNT = ยอด link ของบรรทัดงบนั้น ปันตามยอดที่ขอ (ส่วนเกินลงรายการสุดท้าย)
- **ยอดคงเหลือตอนดึง** ใช้ `SearchBudgetTransferDetail` ตัวเดิม เพิ่มพารามิเตอร์ `receiveIds` กรองด้วย ID (แบ่งก้อน 500 กัน IN เกิน 1,000)
- **แถวงบที่ยอดหมดแล้ว** (view กรองทิ้ง) — หน้าคำขอแสดงยอดคงเหลือ 0 ให้ผู้ใช้ลบเอง / หน้าโอนกลับไม่ดึงมาและแจ้งเตือน

  (สะกด tranfer ตามเมนู) role 1, 31 — ไม่ต้องรันสคริปต์เมนู
  ID 234 "รายละเอียดการแจ้งการโอนเงินกลับ" (`ReportRequestBudgettranfer`, Report) — **ยังไม่ได้ทำ** ไม่อยู่ในขอบเขตรอบนี้

## รอบ 2 (2026-10-14): ค้นหาด้วยเลขที่โอนจัดสรร + กรอกยอดตาม note
ข้อตกลง: ค้นหาด้วย ROUNDNO ไม่บังคับหน่วยเบิกจ่าย/ศูนย์ต้นทุน / เก็บยอดราย note ในตารางใหม่ / กรอกยอดแต่ละ note แล้วยอดแถว = ผลรวม

- **ตารางใหม่** `OAGWBG_BUDGETTRANSFERREQUESTITEM_NOTE` (`02_create_item_note.sql`) — FK cascade ไปที่ ITEM
- **พบว่า view `V_BUDGETRECEIVESUMMARY_REFUND` ไม่ใช่ 1:1** — GROUP BY บรรทัดงบ, `ID = MIN(BUDGETRECEIVE.ID)`
  (ปี 2569: 13,206 จาก 17,287 บรรทัดรวมหลายแถว) แถวรับโอนจัดสรร (type 'A') จึงต้องจับเข้าบรรทัดด้วย key ของ GROUP BY ไม่ใช่ id
- **ค้นหา** (หน้าคำขอ, รูปแบบการค้นหา = 3 "ค้นหาด้วยเลขที่โอนจัดสรร"):
  ROUNDNO → แถว BUDGETRECEIVE type 'A' (`BUDGETALLOCATETRANSFERID` / `...MOREID` สำหรับโอนจัดสรรเพิ่มเติม)
  → จับเข้าบรรทัดงบของ view (key เดียวกับ GROUP BY, ชนกันค่อยใช้รหัสงบ) → `SearchBudgetTransferDetail(receiveIds)` เอายอดคงเหลือ
- **note** ของแต่ละบรรทัด = note ของแถว 'A' ในใบนั้น (`OAGWBG_BUDGETALLOCATETRANSFER_COSTCENTER_NOTE`)
  แถว 'A' ที่ไม่มีแถว note ได้ 1 รายการยอดเต็มแถว (ALLOCATENOTEID = null) — ตรวจแล้วผลรวม note = TOTALRECEIVEAMOUNT ทุกแถว (0 mismatch)
- **บันทึก**: server คำนวณยอดรายการ = ผลรวม note เอง และตรวจ 0 ≤ ยอด note ≤ ยอดโอนจัดสรรของ note / เก็บเฉพาะ note ที่ยอด > 0
- **เปิดคำขอ**: note ที่บันทึก + note ปัจจุบันของใบ (เฉพาะรายการที่เคยกรอกตาม note) ยอดที่บันทึกทับลงไป
- **ดึงไปหน้าโอนเงินกลับ**: หมายเหตุว่างจะประกอบจาก note "ข้อความ ยอด / ..." (ตัดที่ 500 ตัวอักษร)
- ทดสอบ mapping บน PREPROD (read-only, ไม่ยิง GL): 6912575, 6912558, 6910533 (1,120 แถว), 6910858 (note หลายบรรทัด),
  6910033, 6912572 (โอนจัดสรรเพิ่มเติม), 6911171 (ใหญ่สุด 3,185 แถว map 6 วิ) — ทุกแถวลงบรรทัด ผลรวม note = ผลรวมแถว
- **แก้หลังทดสอบ**: (1) ผู้ใช้ค้นในโหมด "ปกติ" แล้วได้ทุกบรรทัดของศูนย์ต้นทุน → รวมโหมด 3 เข้าโหมด 1 = ค้นตามเลขที่โอนจัดสรรบนหัวฟอร์มเสมอ
  (เหลือ 1 = เลขที่โอนจัดสรร, 2 = เลขที่เงินกัน; ร่างที่เก็บ "3" เปิดเป็น "1") และแหล่งเงินบนหัวฟอร์มไม่บังคับแล้ว
  (2) ยอดในแถวเป็นยอดทั้งบรรทัดงบ → `ApplyRoundAmounts`: จัดสรร = ยอดของใบนี้, คงเหลือ = min(คงเหลือทั้งบรรทัด, ยอดของใบ),
  กันไว้เบิก/เบิกจ่าย = "-" (GL แยกตามใบไม่ได้) และแสดงคงเหลือทั้งบรรทัดประกอบ — ใช้ตอนค้นหาและเปิดคำขอ ไม่ใช้ตอนดึงไปหน้าโอนเงินกลับ
  ตรวจกับ API ที่ build ใหม่: ใบ 6912575 บรรทัด 1736 จาก 21,457,500 → 700
- ⚠️ ใบใหญ่ไม่ระบุศูนย์ต้นทุน: ยอดคงเหลือยังต้องยิง GL ทีละบรรทัดเหมือนปุ่มค้นหาเดิม อาจเกิน timeout 5 นาที → หน้าจอแนะนำให้ระบุศูนย์ต้นทุน

## รอบ 3 (2026-10-16): ค้น 2 แบบ + เลขที่โอนของชุดบัญชี + ขอไปแล้ว + ประวัติ
ข้อตกลงกับผู้ใช้:
1. ค้นแบบหน้าโอนเงินกลับเป็นหลัก (ปกติ / เลขที่เงินกัน) + ค้นจากใบโอนจัดสรร (เฉพาะโอนจัดสรร ประเภท 1 สถานะ 80201)

6. หน้าโอนเงินกลับแก้ยอดระดับชุดบัญชีได้ตามเดิม (comment ไว้ว่าอนาคตอาจแก้รายโน้ต) / ไม่เติม REFNO อัตโนมัติ

  — บรรทัดที่ต่าง (54539 ศูนย์ต้นทุนส่วนกลาง ต่าง 15,000) view อ่านยอดจาก V_BUDGETRECEIVE ที่ปรับยอดเพิ่ม ส่วนเราใช้ยอดในตารางตรง ๆ
  (= ยอดที่ V2 ตัดจริง) เอกสารที่เจอต่อบรรทัดสูงสุด 50 (ศูนย์ต้นทุนส่วนกลาง) / 33 (หน่วยงาน)
- **ขอไปแล้ว**: ระดับชุดบัญชี = รายการในคำขออื่นที่ส่งเรื่อง/รออนุมัติ/อนุมัติ และ**ยังไม่ถูกดึง** (ดึงแล้วถังถูกตัดแล้ว)
  ระดับโน้ต = โน้ตในคำขออื่นที่ส่งเรื่อง/อนุมัติ/ครบแล้ว **หรือถูกดึงแล้ว** (ถัง/GL ไม่แยกตามโน้ต) — ไม่นับคำขอที่เปิดอยู่
- **เพดาน server** ตอนบันทึกและตอนส่งเรื่อง: โน้ต ≤ ยอดโน้ต − ขอไปแล้ว / ชุดบัญชี: ยอด + ขอไปแล้ว ≤ ยอดในถัง
  (หน้าจอกันด้วยยอด GL อีกชั้น) — ร่างไม่นับเป็นขอไปแล้ว จึงตรวจซ้ำตอนส่งเรื่อง
- **ประวัติ**: server เทียบกับรายการที่บันทึกไว้ครั้งก่อน — ชุดบัญชีที่เคยเป็นยอดกรอกตรงแล้วรอบนี้เป็นผลรวมโน้ต → บันทึก REPLACE_BY_NOTE
  (ยอดกรอกตรงที่ยังไม่เคยบันทึกแล้วถูกแทนก่อนบันทึก ไม่มีประวัติ)
- หน้าคำขอ: รูปแบบการค้นหา 3 แบบ, แถวรายโน้ตใต้ชุดบัญชีในแท็บ 1 (ยอดโอนจัดสรร | ขอไปแล้ว | ขอได้อีก | กรอก),
  ยืนยันก่อนแทนที่, แท็บ 2 แสดงเลขที่โอนใต้ชื่อรายการ (ใบร่าง/ยกเลิกมีป้าย), ตารางประวัติท้ายหน้า
- หน้ารายการคำขอ: ตัวกรอง "เลขที่โอน" ค้นทั้งเลขที่โอนจัดสรรบนหัวและ ITEM_SOURCE
