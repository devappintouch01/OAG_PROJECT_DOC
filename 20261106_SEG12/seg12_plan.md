# แผนเปลี่ยน Segment12 ที่ส่ง Interface จาก `00` เป็น `0000000`

> สถานะ: **ร่างแผน** (2026-11-06) ยังไม่แก้โค้ด และยังไม่ได้ query DB
> ไฟล์ประกอบในโฟลเดอร์นี้: `โอนจัดสรร.csv`, `โอนกลับ.csv`, `รายงาน.csv`, `ส่งInterface_เรื่องอื่นๆ.csv`, `seg12_flow_queries.sql`

---

## 1. สรุปสั้น

- ฝั่ง GL จะเปลี่ยน Segment12 (Reserve_1) ของชุดบัญชีจาก `00` เป็น `0000000`
- **ข้อจำกัดตอนนี้:** value set `OAG_GL_RESERVE_1` (GL# 50408) ตั้ง MAXIMUM_SIZE = 2 และมีค่าแค่ `00` กับ `T` (ตรวจ PREPROD เมื่อ 2026-11-06)
  ถ้าส่ง `0000000` ไปตอนนี้ `AUTO_COMBINE_ACCOUNT` จะสร้าง CCID ไม่ได้ และได้ error "Can not created account"
- **ปัญหาหลักไม่ได้อยู่ที่โค้ด แต่อยู่ที่ยอดเงิน:** งบ ยอดเงินกัน และ PR/PO ทั้งหมดผูกกับ CCID ที่ seg12 = `00`
  ชุดบัญชีที่ใช้ `0000000` จะเป็น CCID ใหม่ที่ยอดเป็น 0 การเช็คงบ (`find_budget` / funds available) จึงไม่ผ่าน
- ฝั่งเราจึงต้องได้คำตอบจากฝั่ง GL ก่อน (หัวข้อ 3) แล้วจึงตัดสินใจเรื่องข้อมูลเก่า (หัวข้อ 4)

## 4. ทางเลือกเรื่องข้อมูลเก่ากับใหม่

| ทางเลือก | วิธีการ | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **A. ตัดตามปีงบประมาณ** | ปีใหม่ใช้ `0000000` ปีเก่าใช้ `00` ต่อไป | ไม่ต้องย้ายยอด และแยกปีชัดเจน | ปีงบ 2570 เริ่มไปแล้ว จุดตัดถัดไปคือ 1 ต.ค. 2570 งานข้ามปี (กันเหลื่อมปี โอนกลับข้ามปี) ต้องเลือก seg12 ตามปีของต้นทาง |
| **B. ตัดกลางปีแล้วย้ายยอด** | ฝั่ง GL ทำ journal ย้ายยอด B/E จาก CCID `00` ไป `0000000` ณ วันตัด | ใช้ค่าเดียวทั้งระบบหลังวันตัด | ฝั่ง GL ทำงานหนัก ต้องกระทบยอดทุก CCID รวมยอดผูกพันของ PR/PO ที่ค้างอยู่ |

## 5. หลักการฝั่งเรา

1. **อ่าน seg12 จาก config ที่จุดเดียว**
   - ทุก method อ่านจากค่าเดียว เช่น `appsettings.json` → `"GlSegment12": "00"`
   - deploy ขึ้น PROD ด้วยค่า `00` ได้ทันที พฤติกรรมเหมือนเดิม และ hotfix PROD บนโค้ดชุดนี้ได้โดยไม่ต้องแยก branch
   - PREPROD ตั้งเป็น `0000000` เพื่อทดสอบ วันตัดเปลี่ยนแค่เปลี่ยน config
   - ถ้าเลือกทางเลือก A ต้องเลือก seg12 ตามปีงบ (เช่นตั้งค่าเป็นปีที่เริ่มใช้) ไม่ใช่ค่าเดียว
2. **การยกเลิกหรือกลับรายการใช้ seg12 เดียวกับตอนส่งครั้งแรก**
   ตอนนี้หลาย method ประกอบ segment ใหม่ตอนกลับรายการ เช่น `ReverseBudgetAllocateItems` และ `CancelBudgetTransferAdjust`
   ต้องเปลี่ยนให้อ่านจาก `OAGWBG_LOG_INTERFACE` ของบรรทัดต้นฉบับ หรือเลือกตามปีหรือวันที่ของเอกสารต้นฉบับ
3. **โค้ดที่เทียบสตริงชุดบัญชีต้องรองรับทั้งสองค่าในช่วงเปลี่ยนผ่าน**
   เช่น `.00.000` ในหน้าเงินกันส่วนกลาง และการเทียบ PR/PO ในรายงาน
4. **ไม่แก้ seg12 ของใบที่ส่ง interface ไปแล้ว** และไม่แก้ข้อมูล DB เอง
   - `OAGWBG_ACCOUNT_SEGMENT.RESERVE1` (เบิกแทน, เงินนอกงบประมาณ) ใช้ตอนยกเลิก ถ้าแก้ใบเก่าจะยกเลิกไม่ตรง ให้ใช้ค่าใหม่เฉพาะใบที่สร้างหลังวันตัดเปลี่ยน
   - `OAGWBG_BUDGETRESERVEDITEM.ACCOUNTCODE` (เงินกัน) ต้องตัดสินใจร่วมกับ GL (Q9, Q13, Q14) ว่าใบที่ยกข้ามปีจะใช้ seg12 ไหน
   - script ทุกตัวเตรียมไว้ให้ผู้ดูแลรันเอง
5. **ไม่ส่ง `0000000` ไป PREPROD** จนกว่าฝั่ง GL แก้ value set เสร็จ เพราะ auto-combine จะสร้าง CCID ถาวรหรือ error

**33 กรณีทดสอบ** = ส่งรายการใหม่ (23 method ที่ส่ง interface) + ยกเลิกใบเก่าที่ส่งด้วย `00` (~10 กรณี) กรณีหลังเสี่ยงที่สุด
แต่ละกรณีใช้เวลานานเพราะต้องสร้างข้อมูลผ่านหน้าเว็บ ส่ง interface รอ EBS import แล้วตรวจ CCID และยอดใน GL
พ.ร.บ. (โครงการ) และงบเพิ่มเติมยังไม่มีข้อมูลบน PREPROD ต้องสร้างข้อมูลทดสอบใหม่ทั้งหมด

### ข้อสมมติ (ถ้าเปลี่ยน ตัวเลขจะเปลี่ยน)

1. ฝั่ง GL แก้เสร็จและนิ่งแล้ว ถ้าเขาแก้ไปเราทดสอบไป ต้องบวกเวลารอ
2. seg12 เป็นค่าเดียว `0000000` ถ้า Q1 ตอบว่าจะมีค่าที่มีความหมาย ต้องประเมินใหม่ น่าจะเพิ่มหลายสัปดาห์
3. ทำคนเดียวและทำงานนี้งานเดียว ถ้าต้องสลับไปแก้ issue PROD ระยะเวลาจะยืดออก
4. EBS import interface ได้ทันที ถ้าต้องรอ job ตามรอบหรือรอคนฝั่ง GL กด ทุกกรณีทดสอบจะช้าลง
5. ถ้าเลือกทางเลือก A (seg12 ตามปีงบ) บวก 2–3 วัน สำหรับ logic เลือกตามปีและทดสอบงานข้ามปี

### ถ้าต้องการให้เร็วขึ้น

- **แยกคนทดสอบ:** ให้อีกคนสร้างข้อมูลผ่านหน้าเว็บ ส่วนเราตรวจผลด้วย `seg12_flow_queries.sql` งานทดสอบจะลดลงเกือบครึ่ง
- **เรียงทดสอบตามการใช้งานจริง:** ทดสอบงานที่ใช้บ่อยก่อน (พ.ร.บ., โอนจัดสรร, เงินกัน, โอนกลับ)
- **เริ่มงานโค้ดได้เลย:** งานโค้ดประมาณ 9–10 วันแรกไม่ต้องรอฝั่ง GL แล้ว deploy ด้วยค่า `00` ได้ เวลาที่ต้องรอ GL จะเหลือแค่ช่วงทดสอบ

**วิธีได้ตัวเลขจริง:** หลังฝั่ง GL แก้ value set บน PREPROD ให้ทำ spike 1 flow ก่อน (เช่นส่ง พ.ร.บ. 1 ใบด้วย `0000000` แล้วยกเลิก) จะได้เวลาจริงต่อ flow ไปคูณจำนวน flow

### งานที่เสี่ยงที่สุด: เงินกันเหลื่อมปี

1. **เก็บชุดบัญชีเป็นสตริงถาวร:** `ACCOUNTCODE` ในใบเงินกันเก็บทั้ง 13 segment รวม `.00.` ไว้ แล้วนำกลับมาใช้ส่ง interface รอบถัดไป (BG/ENC carry forward) เปลี่ยน config อย่างเดียวไม่ได้ผลกับข้อมูลชุดนี้
2. **ข้ามปีโดยธรรมชาติ:** ใบที่สร้างในปี N ถูกยกไปปี N+1 เสมอ ไม่ว่าจะตัดเปลี่ยนวันไหน จะมีใบที่สร้างด้วย `00` แต่ต้องลงปีใหม่ที่ใช้ `0000000` แน่นอน
3. **ผูกกับ PR/PO ใน EBS:** ยอดผูกพัน (ENC) อยู่บน CCID เดียวกับ PR/PO ถ้าย้ายเงินกันไป seg12 ใหม่แต่ PR/PO ยังอยู่ `00` ยอดผูกพันกับเอกสารจัดซื้อจะแยกกัน
4. **เทียบสตริงกับ EBS:** หน้าเงินกันส่วนกลางเทียบ `ACCOUNTCODE` แบบ `.00.000` กับ `PR_BUDGET_ACCOUNT` / `PO_BUDGET_ACCOUNT` แบบตรงตัว ถ้าฝั่งใดฝั่งหนึ่งเปลี่ยนก่อน รายการจะหายจากหน้าจอ
5. ข้อดีข้อเดียวคือการยกเลิกอ่านจาก log จึงกลับรายการได้ตรง

### อันดับถัดมา: โอนจัดสรร และ พ.ร.บ.

- **ยกเลิกแล้วประกอบชุดบัญชีใหม่ทุกครั้ง** ใบที่ส่งด้วย `00` แล้วมายกเลิกหลังวันตัดเปลี่ยนจะส่ง `0000000` ทำให้ยอดลงคนละ CCID และไม่หักล้างกัน
- **ปริมาณมากที่สุด:** โอนจัดสรร 27,264 แถว / 990 batch, พ.ร.บ. 12,732 แถว
- **พ.ร.บ. คือยอดงบ (B) ตั้งต้นของทุกงาน:** การตัดสินใจทางเลือก A/B/C (หัวข้อ 4) กระทบงานนี้ก่อนงานอื่น

### หมายเหตุเบิกแทน / เงินนอกงบประมาณ

seg12 อ่านจาก `OAGWBG_ACCOUNT_SEGMENT.RESERVE1` ที่เก็บต่อใบ ทั้งตอนส่งและตอนยกเลิก ตอนนี้จึงยกเลิกได้ตรงกับที่ส่งไป
**แต่ถ้า script ไปแก้ `RESERVE1` ของใบเก่าเป็น `0000000` การยกเลิกใบเก่าจะส่งไม่ตรงกับที่ส่งไปครั้งแรกทันที** ดูหลักการข้อ 4

| ความเสี่ยง | ผล | วิธีลด |

| ข้อมูลที่เก็บไว้ยังเป็น `00` | ใบเงินกันเก่าส่ง `00` ต่อ | ตัดสินใจร่วมกับทางเลือก A/B ว่าจะแก้ข้อมูลหรือคงไว้ |

| script แก้ `RESERVE1` ของใบเก่า | ยกเลิกเบิกแทน/เงินนอกงบประมาณใบเก่าไม่ตรงกับที่ส่งไป | หลักการข้อ 4: ใช้ค่าใหม่เฉพาะใบใหม่ |
